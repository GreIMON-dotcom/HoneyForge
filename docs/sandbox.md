# Linux sandbox: реальное выполнение команд

Это отдельный тип `linux-sandbox` уровня high. Старый `telnet-shell` остаётся эмулятором и теперь имеет уровень medium; прежние конфигурации с меткой high нормализуются при чтении.

## Статус проверки

Реализованы контракт, допуск на отдельный узел, политика Docker, управление одноразовым контейнером, шлюз записи, реальный процесс Bash, наблюдение strace, сбор небольших файлов и выгрузка записи. Проверки API и контроллера используют явно обозначенный поддельный Docker Engine. Сквозная проверка на отдельной VM с gVisor в этой сессии не выполнена: адрес подготовленного узла не предоставлен. До неё режим нельзя представлять как проверенный публичный сервис.

## Границы изоляции

На отдельном узле VM/VPS запускаются контроллер, агенты и контейнеры выполнения. Компоненты центра на этом узле запрещены проверкой контроллера. Не размещайте на нём производственные данные или другие приложения.

Один экземпляр содержит три контейнера и два именованных тома:

1. **Шлюз приманки** принимает текстовый Telnet-сеанс, записывает ввод и вывод, создаёт Unix-сокет в томе `/bridge`. Его второй том `/spool` содержит очередь SQLite и конфигурацию.
2. **Агент** видит только `/spool`, имеет удостоверение своего экземпляра и передаёт данные центру по TLS.
3. **Рабочая среда** — отдельный образ Linux с настоящими Bash, Python и утилитами. Запускается только через `runsc` (gVisor), с `NetworkMode=none`, без сети управления, портов и секретов. Единственный том `/bridge` смонтирован только для чтения; рабочий процесс подключается к сокету шлюза. Он не видит очередь и конфигурацию.

Rootfs среды доступен только для чтения. `/home/lab` и `/tmp` — ограниченные tmpfs по 64 МиБ. Пользователь 10001, CapDrop ALL, no-new-privileges, 256 МиБ памяти, 0.5 CPU и 64 процесса. Шлюз и агент имеют собственные лимиты; дополнительные 256 МиБ и 0.5 CPU учитываются в бюджете узла.

После закрытия сеанса рабочий процесс завершается. Контроллер удаляет контейнер и создаёт новый, очищая tmpfs. Дополнительно рабочая среда пересоздаётся по возрасту 10 минут. Это сброс одноразового контейнера к образу, **не snapshot-revert всей VM**. Снимки VM и их восстановление гипервизором не реализованы.

## Какие данные записываются

- Вход с вымышленной учёткой; поле пароля отбрасывается.
- Команды, исходные байты строк ввода и вывод реального Bash, включая последовательность событий и время.
- Вызовы процессов и сети, наблюдаемые через strace. Вызовы connect показывают попытки соединений; внешние соединения запрещены отсутствием сетевого интерфейса.
- Содержимое и SHA-256 обычных файлов до 64 КиБ в `/home/lab` и `/tmp`. Сканирование ограничено 64 файлами и глубиной каталогов; символические ссылки и специальные файлы пропускаются. Часто меняющиеся и сразу удалённые файлы могут не попасть в периодическое сканирование.
- Запись сеанса скачивается в JSON. Файл скачивается как `.bin` с `application/octet-stream`, после проверки целостности SHA-256 и полноты фрагментов. Центр его не исполняет и не отображает как HTML. Наблюдателям выгрузка и содержимое недоступны.

Сеанс строковый, а не полноценный интерактивный SSH-терминал: он не поддерживает все терминальные программы и режимы. Есть лимиты длительности, числа строк, размера ввода и записи (до 256 КиБ переданных от среды данных, до 1024 кадров). При достижении лимита сеанс завершается. Нельзя обещать неограниченную полную запись.

Скачивание инструментов из интернета намеренно не разрешено. Файл можно внести через команды в собственном разрешённом тестовом сеансе, после чего будет записан его небольшой образец. Передача больших файлов, полноценный анализ вредоносных программ и разрешённая сеть для lateral movement не реализованы. Записываются попытки сетевых вызовов, а не атаки на соседние машины.

Запись ввода и вывода выполняется снаружи рабочей среды. strace и инвентаризация файлов работают внутри неё: их данные не являются доказательством, устойчивым к полной компрометации датчика. gVisor также не даёт абсолютной гарантии отсутствия уязвимостей. Администратор VM и Docker остаётся доверенным субъектом.

## Подготовка отдельного узла

1. Подготовить отдельную Linux VM/VPS. Установить Docker и gVisor по [официальному руководству](https://gvisor.dev/docs/user_guide/quick_start/docker/). На VM подходит платформа systrap. Уточнить фактический путь `command -v runsc`.
2. Добавить в существующий `/etc/docker/daemon.json` конфигурацию runtime из `infrastructure/sandbox/daemon.runtime.example.json`, сохранив остальные настройки. Исправить путь к runsc при необходимости. `--host-uds=open` разрешает подключение к единственному переданному Unix-сокету; не передавать другие сокеты или каталоги хоста. Перезапустить Docker на отдельном узле.
3. Настроить частную VPN-связь центра и узла. Центр в примере имеет IPv4 `10.66.0.1`. VPN должна иметь аутентифицированные ключи и ограниченные маршруты. Код проекта не создаёт и не настраивает сам VPN.
4. На центре задать `CENTER_VPN_IP` и добавить `compose.machine.yaml` к обычным файлам Compose. Этот файл публикует машинный TLS-порт 9443 только на IP интерфейса VPN. Сохранить имеющуюся схему запуска центра. Не публиковать машинный порт на `0.0.0.0`.
5. Зарегистрировать узел с доверенного компьютера:

```sh
python infrastructure/sandbox/register_node.py --url https://YOUR-PANEL --id sandbox-1 --vpn-ip 10.66.0.1
```

Скрипт запросит учётную запись администратора, отправит только хеш нового удостоверения контроллера и сохранит секрет в `.sandbox.env`. Для панели с частным CA передать `--ca путь/к/ca.crt`. Бюджет зарегистрированного узла необходимо привести к реальным ресурсам VM в интерфейсе.

6. Перенести на VM репозиторий, `.sandbox.env` и **только публичный сертификат** `infrastructure/certs/ca.crt`. Не копировать `.env` центра, его пароли, закрытый ключ CA или базу. Имя `nginx` разрешается в VPN-IP через управляемые ExtraHosts; TLS проверяет сертификат по имени nginx.
7. Применить firewall на VM, где уже запущен Docker:

```sh
sudo sh infrastructure/sandbox/firewall.sh 10.66.0.1
```

Правила запрещают новые подключения мостов hfh-* к самому узлу. Из сети управления разрешена только передача к VPN-IP центра на TCP 9443; из других мостов новые исходящие соединения блокируются. Правила не меняют входящий SSH снаружи и не сбрасывают остальной firewall. Docker-сети конфигурации используют IPv4, IPv6 не включается.

Настроить восстановление этого скрипта после запуска Docker и VPN при каждой загрузке VM, например собственной службой systemd с `After=docker.service network-online.target`. Использовать постоянный абсолютный путь к скрипту и VPN-IP в ExecStart. Скрипт создаёт `/etc/honeyforge/sandbox-guard.json` с идентификатором текущей загрузки. Контроллер проверяет эту отметку; после перезагрузки устаревшая отметка не принимается. Отметка подтверждает запуск скрипта доверенным владельцем, а не защищает от последующего изменения firewall администратором.

8. Собрать оба образа и запустить только инфраструктуру отдельного узла:

```sh
docker compose --env-file .sandbox.env -f infrastructure/sandbox/compose.yaml --profile build build
docker compose --env-file .sandbox.env -f infrastructure/sandbox/compose.yaml up -d
docker compose --env-file .sandbox.env -f infrastructure/sandbox/compose.yaml logs controller
```

Контроллер проверит сети, отсутствие компонентов центра, runtime runsc и образ. Затем создаст временные контейнеры и проверит реальное выполнение команды, strace, сбор файла и Unix-сокет через read-only mount. Только после успешной проверки он сообщит центру `sandbox.ready=true`.

При несовместимом runtime, неработающем сокете или датчике режим закрыт. API не допустит развёртывание на локальном узле центра или неподготовленном узле. Мастер предложит только одобренные подключённые узлы с подтверждённой возможностью sandbox.

## Проверка после запуска

Создать экземпляр Linux sandbox в интерфейсе, выбрать отдельный узел и дождаться работающих трёх контейнеров. Для первого теста публиковать один порт только на loopback VM, например 8024. По SSH на VM подключиться к этому локальному порту обычным Telnet-клиентом. Использовать вымышленные данные входа.

Проверить `id`, `pwd`, создание небольшого текстового файла в `/home/lab`, чтение этого файла и `exit`. В центре сверить ввод, вывод и файл; скачать запись и сравнить SHA-256. Повторно подключиться и убедиться, что файла уже нет, а ID рабочего контейнера изменился. Отдельно проверить отсутствие исходящих соединений, доступ к центру из рабочей среды и удаление всех контейнеров/томов при удалении экземпляра.

Внешнюю публикацию включать отдельно только после этих проверок. Регистрация узла и наличие типа в каталоге сами по себе не подтверждают успешный запуск high-interaction среды.
