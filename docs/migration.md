# Переход с версии двух слотов

Версия 1.0 запускала ровно две ловушки как сервисы Compose: `honeypot-low` с `agent-low` и `honeypot-medium` с `agent-medium`. Версия 2.0 создаёт ловушки динамически. Обновление сохраняет пользователей, профили, события, оповещения и журнал аудита.

## Что изменится

| Было | Стало |
|---|---|
| Сервисы `honeypot-low`, `honeypot-medium`, `agent-low`, `agent-medium` в `compose.yaml` | Сервис `controller`; контейнеры ловушек создаются по запросу |
| Узлы `lab-low` и `lab-medium`, по одной ловушке на узел | Узел `lab-docker` с политикой ёмкости |
| Секреты `AGENT_LOW_TOKEN`, `AGENT_MEDIUM_TOKEN` в `.env` | Секрет `CONTROLLER_TOKEN`; секреты агентов создаёт контроллер |
| Изменение профиля сразу меняет ловушку | Ловушка хранит снимок конфигурации; новая версия профиля применяется по политике экземпляра |
| Скрипт `local_host.py` для дополнительных узлов | Не нужен и удалён: любое число ловушек создаётся в интерфейсе |

Две существующие ловушки сохраняют идентификаторы, названия и всю историю событий. Контроллер создаёт для них новые контейнеры и удостоверения агентов. Прежние агенты `low` и `medium` остаются в базе как источник старых событий и больше не могут подключаться.

## Порядок обновления

1. Сделайте резервную копию базы данных при работающей версии 1.0:

   ```sh
   docker compose exec -T postgres pg_dump -U honeyforge honeyforge > backup-before-2.0.sql
   ```

2. Получите исходный код версии 2.0 в тот же каталог, не удаляя `.env` и `infrastructure/certs`.

3. Добавьте секрет контроллера. Остальные значения `.env` и сертификаты сохраняются:

   ```sh
   python infrastructure/scripts/setup.py
   ```

4. Пересоберите и запустите. Ключ `--remove-orphans` удаляет четыре прежних контейнера ловушек и агентов:

   ```sh
   docker compose up --build -d --wait --remove-orphans
   docker compose restart nginx
   ```

   Сервис `migrate` применяет миграцию `e7a4d2c91f30`. Перезапуск `nginx` загружает новую конфигурацию с каналом контроллера.

5. Через 10–30 секунд откройте «Все ловушки». Перенесённые ловушки должны вернуться в прежнее состояние: работавшая — «Работает», остановленная — «Остановлена». События доступны в прежнем объёме.

6. Удалите тома очередей прежних слотов, когда убедитесь в результате:

   ```sh
   docker volume rm honeyforge_low-spool honeyforge_medium-spool
   ```

   Перед обновлением очереди обычно пусты. Событие, которое оставалось в очереди слота в момент обновления, в базу не попадёт.

Строки `AGENT_LOW_TOKEN` и `AGENT_MEDIUM_TOKEN` в `.env` больше не используются; их можно удалить.

## Проверка результата

```sh
docker compose ps
docker ps --filter label=io.honeyforge.managed=true
python infrastructure/scripts/demo.py
```

Сервис `controller` должен быть в состоянии `healthy`. Вторая команда показывает по два контейнера на каждую развёрнутую ловушку. Демонстрация создаёт шесть экземпляров, проверяет их и удаляет за собой.

## Возврат

Обратная миграция схемы не предусмотрена. Для возврата остановите лабораторию, восстановите резервную копию в пустую базу и запустите исходный код версии 1.0:

```sh
docker compose down
docker volume rm honeyforge_database
# вернуть исходный код версии 1.0
docker compose up -d postgres
docker compose exec -T postgres psql -U honeyforge -d honeyforge < backup-before-2.0.sql
docker compose up --build -d --wait
```

Контейнеры и тома, созданные контроллером версии 2.0, удалите вручную по метке `io.honeyforge.managed=true`, как описано в [инструкции по эксплуатации](deployment.md).

## Что проверено

Миграция проверена автоматическим тестом на SQLite (`tests/test_migration.py`), на копии рабочей базы PostgreSQL с 62 событиями и 292 записями аудита и на самой рабочей лаборатории. Сравнение моделей со схемой (`alembic check`) расхождений не показало. Подробности — в [отчёте о проверках](status.md).
